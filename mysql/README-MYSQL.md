# MySQL 迁移说明（给研发）

原方案跑在 Supabase（PostgreSQL）上。这里是翻译好的 MySQL 版本，用来在公司环境打通流程。

## 文件

| 文件 | 内容 | 备注 |
|---|---|---|
| `01_schema_mysql.sql` | 10 张表 + 3 个身份函数 + 4 个隔离视图 | 幂等，可重跑 |
| `02_seed_data_mysql.sql` | 真实两期数据（月度 102 家 + 周度 93 家） | **含真实商家评级，公司内部数据，勿入公开仓库** |

执行顺序：

```bash
mysql -u <user> -p <db> < 01_schema_mysql.sql
mysql -u <user> -p <db> < 02_seed_data_mysql.sql
```

要求 **MySQL 8.0.16+**（用到 `JSON` 类型与 `CHECK` 约束），字符集 **utf8mb4**
——商编码和显示名里有西语重音字符（`ENVÍAGUIA`、`MONDRAGÓN`、`RÁPIDITOS`）。

`02` 末尾自带自检查询，跑完应看到：

```
vg_periods             2      月度 1 + 周度 1
vg_vendor_profile      102
vg_vendor_scores       195    月度 102 + 周度 93
vg_rules_public        1
```

月度 `2026-07` 的等级分布应为 **S=3 / A=26 / B=57 / C=16**（S+A 占比 28.4%）。
对不上就说明导入有问题，先别往下走。

## ⚠️ 最要紧的一件事：隔离机制没了

原方案的数据隔离**完全由 PostgreSQL 的行级安全（RLS）在数据库层强制**：

- Vendor 登录后，数据库**只会返回他自己那一行**——即使他绕过前端、直接构造 API 请求也一样
- RM 只能看到「自己名下 ∪ 全部 S 级」
- 内部规则表（备选分数线、SA 占比目标）只有主管理员能读
- 未登录状态直接请求任何表 → 返回 0 行

**MySQL 没有行级安全。** 上面这些表建完之后，隔离能力为零：任何能连库的人都能读全表。

### 这为什么要紧

这是个对外系统，商家之间是竞争关系。**一个商看到另一个商的单量、得分、欠款红线状态，
是事故级问题**，不是体验问题。原方案把它放在数据库层，正是因为应用层漏一个 `WHERE`
条件就全量泄漏，而且**漏了之后页面看起来完全正常**——前端也在过滤，肉眼发现不了。

### 建议怎么做

1. **主防线：应用层收敛到唯一的数据访问入口。** 所有查询都必须经过它，由它按当前登录身份
   注入过滤条件。不要让业务代码直接拼 SQL 查这些表。
2. **第二道防线：`01_schema_mysql.sql` 末尾的函数与视图。** 用会话变量表达了原 RLS 的可见范围（MySQL 的视图定义禁止引用用户变量，所以身份要先经存储函数读出来）：

   ```sql
   SET @vg_user_id = '<当前登录用户标识>';
   SELECT * FROM v_vg_vendor_scores WHERE period = '2026-07';
   ```

   注意：用连接池时必须保证「设变量」和「查询」在**同一条连接**上，请求结束后清理，
   否则会串号——这套方案最容易在这里出事。如果公司平台已有成熟的数据权限中间件，优先用它。
3. **必须有越权测试，并且进 CI。** 原方案有一个 41 项断言的脚本（`scripts/test_rls.js`），
   核心是两条：
   - 用 Vendor A 的身份请求 Vendor B 的数据 → 断言返回为空
   - 用未登录身份直接请求所有表 → 断言返回为空（**这条最重要**）

   建议在 MySQL 版本上照着重写一份。RLS 配错时页面看起来完全正常，只有这类脚本能发现。

### 各角色应该看到什么

| 角色 | `vg_vendor_scores` / `vg_vendor_profile` | 内部规则表 |
|---|---|---|
| `vendor` | 只有自己那一行 | 不可读 |
| `rm` | 自己名下 ∪ 全部 S 级 | 不可读 |
| `ops` | 全部 | 不可读 |
| `admin` | 全部 | 可读 |

分布与等级聚合表（`vg_score_distribution` / `vg_level_counts`）不含任何身份信息，
任何登录角色都可读——Vendor 端画分布图要用。

## 几个字段的坑

**`indicators`（JSON）** —— 六项指标的值、得分、权重与档位。页面直接消费这个结构，
字段名不要改。形状：

```json
[{"key":"orders","name_key":"indicator.orders","weight":0.3,"value":5434.77,
  "unit":"完美单/日","score":100,"contribution":30,
  "tiers":[{"gte":1250,"score":100},{"gte":500,"score":80},
           {"gt":100,"score":50},{"gte":0,"score":0}]}]
```

注意档位里有 `gte`（含边界）和 `gt`（严格大于）两种算子，**不能当成一样的**：
`gt` 是为了让边界值落进 0 分档（对外公示要求边界归属明确）。

**`rank_all` / `rank_city` / `rank_level`** —— 名次必须在**导入时预计算**写进这一行。
原因：原方案下 Vendor 只能读到自己 1 行，页面没法遍历全网算名次。即使 MySQL 侧能查全表，
也请保留预计算——否则每个 Vendor 打开页面都要全表扫一遍，而且名次口径容易和导入时算的不一致。

**`first_order_date` 可以为空**（现有 4 家）。为空时页面必须显示「未知，待补数据」，
**不得默认成「已过保护期」**——那会让新商收到错误的清退警告。

**`rm_name` 可以为空**（现有 4 家未分配 RM）。不要就近分配。

**`period` 有两类**：月度（`2026-07`）是正式评级；周度（`2026-W32`）是试算快照，
`disclaimer = 1`，不计入新商保护期与清退累计。页面按 `period_type` 区分展示。

**`total_score` 用 `DECIMAL`，不要用 `FLOAT`** —— 分数线判定是等号敏感的
（如「≥ 55 才是 A」），浮点误差会让边界上的商家等级跳变。

## 计分逻辑不要重写

`src/engine/` 是零依赖的纯 JS 计分引擎，同时被浏览器、校验脚本和单元测试引用。
**不要为了后端方便再实现一份**——一旦有两份，迟早出现「页面显示 A、结算按 B」。
它可以直接搬到服务端运行。

同理，等级规则（权重、档位、分数线、单价、红线参数）全部在 `vg_rules_public.body` 这个 JSON 里，
**不要把任何阈值硬编码进代码**。分数线会随市场定期校准，硬编码会让代码与对外公示的规则分叉。
